I built a desktop in ten days or less

compost is a new desktop for Linux: a window system in the spirit of MGR, with the shapes of the classic Macintosh and Plan 9's way of joining programs. Claude sessions wrote it in eight days, from a design I could read and check.

Written by Claude, for Friday

BUILT code and a passing test PARTIAL some of it built PLANNED designed, not built

What compost is

compost is a window system in which a program controls its window only through the bytes it writes, as in MGR.

MGR came from Bellcore in 1988 and made every window a terminal. A program drew, made menus and read the mouse by writing control sequences to its output and reading replies on its input. A shell script could draw, and so could a program at the far end of a remote login.

Nothing offers that model on Linux today. compost rebuilds it with a protocol of its own and draws straight to the kernel's display interface at 4K. The server is Erlang/OTP, one process per window, so a client that breaks its window breaks only that window. Rust covers what must be native: the display, input, terminals and the loops over pixels.

On top sit a desktop with System 6's shapes in a quiet Platinum finish, a terminal that tmux and Claude Code run in, plan9port's acme and plumber, a browser called battuta, and wl, which gives each Wayland app a window of its own.

Claude sessions wrote the code. I wrote down what compost should be and made the choices. After eight days, 156 implementer runs had built 1,652 specs, each a testable line of the design with code and a passing test behind it.

The ideas

Four ideas shape compost: a window is a byte stream, everything else is a file, garden lives on the desk, and the look is System 6.

Every window is a byte stream

BUILT

Anything that can print can draw, even over ssh, because it is only bytes.

A program titles its window, draws bitmaps, adds menu items and claims the mouse by writing commands into its terminal stream; events come back on its input. The cat clock is a Python script with no library beyond Python's own, and the lab checks that it draws the same frames over ssh as locally. Remote use as a whole is still PARTIAL.

The rule holds for the browser too. battuta renders each page with WebKit, off screen, and sends its window the rows that changed.

Everything outside a window is a file

PARTIAL

Scripts reach windows through a 9P file tree, and programs reach each other through the plumber.

Through the window tree a script can open, move, hide and close windows, read their text and send them bytes: whatever I can do with the mouse and keys. A program acts on its own window through its stream; anything outside the window uses the files.

plan9port's plumber runs with the session. Ctrl+click a file name in a terminal, double-click it in a folder or follow a link in Help, and one plumb message goes out; one table of rules picks the program. The design's first tenet is compose before adding: a feature between programs is built from plumbing rules and files that already exist, and nothing is added for tests alone.

garden lives on the desk

PARTIAL

garden is my plain-file home for tasks and documents, and compost reaches it as a shell does: through its tool, its file tree and the plumber.

garden, a separate project of mine, is a folder of plain files, with todo.txt for tasks, that one small daemon guards and serves as a 9P tree. The daemon checks every save and can refuse it. When two devices meet they merge, and where both changed the same place, both versions are kept.

In compost, garden's people, tags, projects, tasks and kinds of document are drawers on the desk, and the day's tasks and habits drop down from the clock. compost never writes garden's folder itself, so the daemon's checks always apply.

System 6 shapes, Platinum finish

PARTIAL

compost looks and behaves like the Macintosh of System 6, drawn with its own artwork in a quiet Platinum style.

A menu bar runs across the top. Windows have title bars and close, zoom and grow boxes, and one mouse button does everything. The focused window has stripes; the rest go flat and light, as in Mac OS 8. Each folder opens in one window that reopens where I left it. Where System 6 had nothing to copy, such as Wi-Fi or switching windows by key, compost behaves as GNOME does. Text is bitmap fonts, enlarged only by whole numbers, so it stays sharp at 4K.

How it was built in about ten days

Many Claude sessions worked in parallel from one written intent, and my attention went only to real choices.

Linked-Intent Development (LID) sends intent one way: a high-level design, a design for each part, then specs, tests and code. Each level is written so the next can be built from it alone.

The arrow

Every spec is one testable line with an ID that tests and code cite.

CAT-005: The cat clock shall start a new frame about every 50 ms, and the swing p shall follow sin(2π·t/1 s), so the eyes and tail complete one swing per second.

Every document is written to be read cold, so a fresh session can take any piece without the conversation behind it. That is what let sessions work side by side.

Clean-room implementers

An implementer is a headless Claude session in a container holding only the repository.

The design restates MGR's behaviour in the project's own words, and the code is written from the design alone. Implementers have no web tools and never see MGR's code or manual; a script checks this before every run. Most prompts carry one rule: write the test, watch it fail for the right reason, then write the code.

Reviews, a decision log and a coordinator

Reviewers attack each design before code exists, sessions log their own small decisions, and one coordinator relays my answers.

Review sessions try to disprove a design, and later the code before it reaches my login. A session that meets a gap takes the reading closest to the design's tenets, carries on, and logs the question, the answer, the alternatives and the reason. Only real choices reach me: what I'd see, cost, my data, credentials, forks in the design. A branch merges without asking me once every device-free suite and the lab VM's tests pass.

The review that caught Vulkan's numbering

The GPU design would have drawn 12 of compost's 16 raster functions wrong, and a review caught it before any code existed.

compost draws with 16 exact bitwise functions and no alpha. Of the GPU interfaces I weighed, only Vulkan's logic ops offer all 16, so the design drew function n with Vulkan's op n. Both name the same truth tables, but Vulkan orders each table's bits the other way round. Only 4 of the 16 survive that, and copy, the function that puts a picture on screen, isn't among them. The review marked it a blocker, and a spec now tests every function against every pair of bits.

From a sentence to my login

About fourteen hours passed between my deciding to draw on the GPU and my own session composing on it.

Overnight came a design, the review above and an implementer run, and by morning the GPU passed its tests in the lab's VM. On my own machine the first login said GPU off: reading back the screen's image failed, so compost stayed on the CPU, as designed. A fix was designed that morning, and the next preview image composed on the GPU.

What I'd tell someone trying this

Write the intent so a stranger could build from it, and spend your own time only on choices.

  • Write every document to be read cold. A session that needs the conversation behind a document will guess.
  • Keep specs small. One line, one behaviour, one ID. When tests and code cite it, a gap shows.
  • Let sessions settle small questions, and log every answer. Give them tenets to lean on, then read the log.
  • Review designs, not only code. A bug found before the code exists costs a paragraph. Ask reviewers to disprove, not approve.
  • Let status lag the code, never lead it. Nothing is built until code and a passing test both exist.
  • Expect the machinery to break in ordinary ways. Two sessions took the same spec ID, so IDs are now claimed first in one shared file. Timing tests failed when many runs shared one machine, so a flaky test is logged and rerun once, and fixed if it fails again. Parallel branches still need someone to merge them.
  • Guard your attention. It is the one thing the sessions can't multiply.

LID didn't make the code easy. It made the intent plain enough to hand off, and to recognise when it came back.
