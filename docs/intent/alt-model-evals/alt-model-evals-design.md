# Alternate-Model Eval Runs

## Context and Design Philosophy

LID's behavioral eval suites (`plugins/*/skills/*/evals/evals.json`) run on Claude models, through `skill-creator` and `claude -p`. LID itself is meant for any model a user pairs it with, and its skills are written for an average executor, not a strong one. A suite's results say nothing about models it never ran on (HLD tenet *Design for the pair, not the model*). This segment owns the repository runner that executes those same suites on models from other providers, reached through OpenRouter, so the evidence behind LID's guidance can cover more than one model family.

Four principles shape the component:

- **Optional evidence, never a gate.** Alternate-model runs add evidence: a new `tested_with` entry, material for a capability-flag noise study, a signal that a skill's wording works only on strong models. They are never part of the merge gate (HLD § *Code and tests for LID*), and no contributor needs an OpenRouter account, a key, a container runtime, or the runner to contribute. The runner is a maintainer helper under *LID runs on the agent, not a runtime*: it may speed up evidence gathering, but nothing requires it.
- **Same eval, different executor.** A run uses the suite's own fixture files, its own prompt, and its own assertions, graded the same way as a Claude run. Only the model and the agent harness around it differ, so an alternate-model result can sit next to a Claude result and be compared directly.
- **The model sees the fixture and the skills, nothing else.** Each run executes inside a container that holds only the fixture project, a read-only copy of the plugins, and the harness. No instruction file, skill, plugin, credential, or file from the machine running it reaches the model. Neither does anything that reveals the expected answer: the eval's assertions, the eval's name, or earlier runs. This holds against a model that deliberately goes looking, not only against accidental leaks.
- **A real harness behind a thin wrapper.** The model works inside a shipping, open-source coding agent with ordinary file and shell tools, the kind of environment LID users actually run. The repository owns only the wrapper: fixture staging, the sandbox, invocation, and output capture. The harness's maintainers own the tool loop.

The runner and its Dockerfile are ordinary code and walk the standard arrow (`HLD → LLD → EARS → tests → code`). They ship in no plugin bundle and are never installed into a user's project.

## Harness

The harness is **opencode** (`opencode-ai` on npm), run headless as `opencode run`. It speaks to OpenRouter natively (`-m openrouter/<model-id>`), emits a JSON event stream (`--format json`) that serves as the run's transcript, gives the model read, write, edit, glob, grep, and bash tools, and works in whatever directory it is started in.

The harness version is **pinned** in one constant in the runner, baked into the container image at build time, and recorded with every run. It changes only by a deliberate edit, because a harness upgrade can change results as much as a model change can. A version bump rebuilds the image, confirms which instruction files the new version loads (below), and reruns a sample of earlier alternate-model runs before new results are compared with old ones. Past `tested_with` entries keep the harness they recorded.

Invocation flags:

- `--pure` — no external harness plugins.
- `--auto` — tool permissions are granted without prompting. A run is non-interactive, and everything the model can touch is disposable.
- `--format json` — the event stream on stdout.
- stdin is closed. `opencode run` reads piped stdin as extra message text and waits on it indefinitely when stdin is open.

The harness reads a configuration file generated by the runner, containing exactly: automatic updates off (`"autoupdate": false`), session sharing off (`"share": "disabled"`), and the OpenRouter provider's API key as the environment reference `{env:OPENROUTER_API_KEY}`.

The fixture's own instruction files (`AGENTS.md`, `CLAUDE.md`) load according to the harness's own rules for any project. That is what a real user of the harness gets. Which files a given harness version loads is confirmed when the pin changes, because the Claude runs load the fixture's `CLAUDE.md` and a difference there is a difference in what the executor was told.

## Sandbox

Each run executes in a container, started through the `docker` command-line interface. Any runtime that provides it works: colima, Docker Desktop, OrbStack, or Podman's Docker-compatible interface.

**Image.** `tools/alt-model-evals/Dockerfile` builds from a pinned Node base image and adds `git`, `ripgrep`, and `opencode-ai` at the pinned version. The runner tags the image with the harness version and a hash of the Dockerfile, and builds it on first use when no image with that tag exists.

**Container.** The runner starts one container per run with:

- the fixture project mounted read-write at `/work/project`, which is the working directory;
- the staged plugins mounted read-only at `/work/plugins`;
- the generated harness configuration mounted read-only at `/work/opencode.json`, outside the project, and pointed at by `OPENCODE_CONFIG`;
- a private, in-memory home directory (`/home/eval`) and `/tmp`, and an otherwise read-only root filesystem;
- the host user's UID and GID, so files the model writes are owned by the person running the runner, with generated one-line `/etc/passwd` and `/etc/group` files mounted read-only so tools that look up the current user (Node's `os.userInfo()` among them) find an entry;
- all Linux capabilities dropped, privilege escalation disabled, a 2 GiB memory limit, and a 512-process limit;
- an environment holding only the OpenRouter key, the home directory, a git author and committer identity (so a skill that commits works), and locale basics;
- network egress, which the harness needs to reach OpenRouter.

The harness is invoked with a direct argument list, never through a shell. Nothing else from the host is mounted. The model cannot read the repository checkout, the invoking user's home directory, or other runs, even with a shell and absolute paths.

**Capture stays in the sandbox.** Everything in the project directory, `.git/` included, was writable by the model, so the host treats that directory as untrusted after the harness starts. Git in particular executes programs named in a repository's own configuration and attributes (`core.fsmonitor`, filter drivers, diff drivers, hooks), and a `.git` that is a symbolic link or a `gitdir:` file can point git at a directory outside the project. The runner therefore never runs git on the host in the project directory once the harness has started. The change patch and git log are produced by a second, short-lived container from the same image and with the same hardening, which mounts the project read-write and an empty output directory, has no network and no key, and runs a fixed capture step: remove a stale `.git/index.lock`, stage everything into a temporary index, write the patch against the fixture commit, and write the log. Anything the model planted in `.git/` can fire only inside that throwaway container; the worst it can do is falsify its own run's patch, which the model could already influence by editing files. On the host, the runner only copies the project — preserving symbolic links as links without following them, and skipping FIFOs, sockets, and device files — and redacts the copy.

**Memory.** The harness itself dominates memory use: opencode peaked at about 1.2 GB resident during a five-minute `lid-coach` run, and a run's in-memory home and `/tmp` count against the same budget. The 2 GiB limit leaves headroom above that peak while still stopping a runaway process. On macOS and Windows the containers run inside a VM whose memory is fixed when the runtime starts, and colima's default is 2 GiB, shared with every other container on the machine. A VM with less total memory than the container's limit cannot run it at all, so the runner checks the runtime's total memory before staging anything and stops with the two numbers when it falls short. The check catches only that impossible case: a VM that clears it can still run out mid-run when other containers share it, and that surfaces as a `harness_error` with exit code 137. About 4 GiB for the VM is the practical recommendation.

**What the model can still reach.** The container has to hold the OpenRouter key so the harness can call the API, and the bash tool can read it (`echo $OPENROUTER_API_KEY`). Network egress is open. A model could therefore send the key somewhere. Two measures bound this. First, the runner redacts every literal occurrence of the key from the captured outputs (below); a copy the model deliberately encodes (base64, split across lines) is not caught. Second, contributors are advised to run evals with a dedicated OpenRouter key with a low credit limit, so a leaked key is cheap to lose and revoke.

**Running without a container.** When no `docker` interface is reachable, the runner stops and says so. `--no-container` runs the harness directly on the host, through `npx`, with a throwaway `HOME` and `XDG_*` root and an environment reduced to an allowlist (the key, `PATH`, the throwaway home, git identity, locale). This hides the user's configuration and credentials, but it is not a filesystem boundary: a model with a shell can read any file the user can. The runner prints that warning before starting and records the mode in the batch record. The npm cache stays at the user's own location so each run does not download the harness again.

### Credentials

The OpenRouter key comes from `OPENROUTER_API_KEY` in the environment, the name the harness and most OpenRouter clients already use. With no key, the runner stops before staging anything and names the variable.

The runner never puts the key on disk or in a process listing: not in the generated configuration, not in the arguments of any process it starts (`docker` receives it by name and inherits the value). The capture container does not receive it at all. Before a run's outputs are written to the workspace, every captured regular file — the transcript, stderr, the final response, the change patch, the git log, and every file in the captured project — has each byte-for-byte occurrence of the key replaced with `[REDACTED]`. Redaction treats every file as bytes rather than guessing which files are text, leaves symbolic links alone, and keeps each file's mode.

## Staging a run

For each run, the runner creates a scratch directory with a random name under `$XDG_CACHE_HOME/lid-alt-evals/` (`~/.cache/lid-alt-evals/` by default). The location sits under the user's home directory because container runtimes share the home directory with their VM by default — colima and Docker Desktop on macOS, Docker's WSL integration on Windows — while the system temp directory (`/var/folders/…` on macOS) is often not shared, and a mount from it would come up empty inside the container. The directory's parent path is never visible inside the container.

```
~/.cache/lid-alt-evals/<random>/
  project/        ← the eval's fixture files, as a fresh git repository with one commit
  plugins/        ← a copy of the repository's plugins/ tree
  opencode.json   ← the generated harness configuration
```

- **Fixture.** Each entry in the eval's `files` list is written under `project/` at its `path`, with its content exactly as given. A path that is absolute, contains a `..` segment, or begins with a `.git` segment is a malformed suite: the runner checks every selected eval's paths before running anything, and stops if any is malformed. The directory is initialized as a git repository and committed once with a fixed identity and the message `fixture`, so skills that read history or diff against `HEAD` behave as in a real project. An eval with no files gets an empty commit, with no placeholder file.
- **Skills.** The whole `plugins/` tree is copied, mirroring its repository layout, because skills reach outside their own directory: `lid-coach` reads a sibling skill's `references/capability-flags.md`, `update-lid` reads its plugin's `plugin.json` for the version, and `map-codebase` links into another plugin by relative path. The copy excludes every `evals/` directory and every `*-workspace/` directory, at any depth, so no assertion and no earlier run output is reachable.

Paths inside the container (`/work/project`, `/work/plugins`) are fixed and neutral. The eval's name appears nowhere the model can see.

### The run prompt

The model receives one message, built from a fixed template shared by every run:

1. It is executing one eval run of an agent skill; the current directory is the project root and the entire repository.
2. Read the skill at `/work/plugins/<plugin>/skills/<skill>/SKILL.md`, and any references it directs you to. Sibling skills live under `/work/plugins/`.
3. The user's request, quoted verbatim from the eval's `prompt`. Execute it per the skill against the current directory, making any file changes yourself.
4. The run is non-interactive: where the skill would ask the user, take the skill's stated default and state in the final response which defaults were taken. Today's date is the run date.
5. The final message is the exact user-facing response and nothing else.

This matches the prompt the Claude pilot runs use, except that it names an "agent skill" rather than a Claude Code skill. In `--no-container` mode the plugin path is the scratch directory's `plugins/`.

## Run lifecycle and status

Each run has a wall-clock limit on the harness, **10 minutes** by default and set with `--timeout`, measured from the moment the harness starts, so staging and a first-use image build do not count against it. The slowest Claude run on record in the pilot workspaces took just over 9 minutes; most finish in two to four.

A run ends in exactly one status:

- **`completed`** — the harness exited zero and emitted no top-level `error` event (a line of the event stream whose own `type` is `error`). A tool call that failed and that the model worked around is model behavior, not a harness error. Graded. A completed run with an empty final message is still graded, and its response assertions fail.
- **`harness_error`** — the harness exited non-zero or emitted a top-level `error` event (a rejected key, an unknown model, a model without tool support, an API failure the harness gave up retrying). Not graded: it says nothing about the skill.
- **`timeout`** — the run hit its wall-clock limit and was killed. Not graded, and reported beside the pass rates, since a model that loops until the limit is a result worth seeing.
- **`interrupted`** — the person running the batch stopped it (Ctrl-C, a cancelled shell). Not graded and not reported: it says nothing about the model or the skill.

Outputs are captured for every status, including partial project state from errored, timed-out, and interrupted runs.

On timeout, on an interrupt, and on any runner failure, the runner stops the container (or, without a container, the harness's whole process group) with a termination signal, kills whatever remains after 10 seconds, captures what exists (the capture step clears any stale git lock the kill left behind), and removes the scratch directory. After two consecutive `harness_error` runs anywhere in the batch, the runner stops the batch: a bad key or model ID would otherwise fail every remaining run.

## Outputs

Runs land in the skill's gitignored workspace, beside the Claude runs, in the per-eval shape `skill-creator`'s grader reads:

```
plugins/<plugin>/skills/<skill>-workspace/alt-model-<YYYY-MM-DD>-<model-slug>/
  batch.json
  eval-<id>-<name>/
    eval_metadata.json        ← eval_id, eval_name, prompt, assertions (copied from evals.json as-is)
    with_skill/run-<n>/
      events.jsonl            ← the harness's JSON event stream: the transcript
      response.md             ← the model's final text message
      timing.json
      stderr.log
      changes.patch           ← every difference from the fixture commit, untracked files included
      git-log.txt             ← the project's history, including any commits the model made
      project/                ← the fixture directory's final state, without .git
```

- Runs within a batch go eval by eval, in ascending ID order, all runs of one eval before the next.
- `<model-slug>` is the OpenRouter model ID with every character outside `[A-Za-z0-9._-]` replaced by `_`. `<name>` is the eval's `eval_name`, sanitized the same way. `<YYYY-MM-DD>` is the batch's start date. Runs are numbered from 1.
- A second batch for the same model on the same day gets a numeric suffix. The runner claims the directory by creating it, so two concurrent batches cannot take the same one.
- `project/` preserves symbolic links as links and keeps file modes, so assertions about symlinks and executables can be graded. FIFOs, sockets, and device files are not copied.
- `response.md` is the text of the last event of type `text` in the stream. Each such event carries one complete text part (opencode emits a part when it finishes, not as streamed fragments), so the last one is the model's final message. Reasoning and tool output never count as the response. `git-log.txt` is `git log --stat` from the final `HEAD`.
- `changes.patch` and `git-log.txt` let a grader check that a run changed nothing, or exactly what it changed, without the stripped `.git`.

`timing.json` records: `model` (the OpenRouter ID), `harness` (`opencode-ai@<version>`), `status`, `duration_ms`, `total_cost_usd` and token counts summed from the event stream (`null` when the stream carries none), the number of tool calls, `exit_code`, and `error_message`.

`batch.json` records the skill, eval IDs, model, variant, harness, sandbox mode (`container` or `none`), timeout, run count, the repository's `HEAD` commit, the **git tree ID of `plugins/` as staged**, whether that tree matches `HEAD`'s, and the batch state (`running`, then `complete` or `aborted`).

The tree ID identifies exactly the skill text a batch ran against, whether or not it was committed. The runner computes it with a temporary git index over the on-disk `plugins/` directory (tracked and untracked files, gitignored ones excluded), leaving the repository's own index, working tree, and history untouched. Running on uncommitted skill edits is normal — it is how a skill change is tried out — and the runner never refuses it.

## Invocation

```
tools/alt-model-evals/run_eval.py <skill> <eval-ids> <model> [--runs N] [--timeout SECONDS] [--variant NAME] [--no-container]
```

- `<skill>` is a skill directory name (`lid-coach`, `update-lid`, `arrow-maintenance`, `map-codebase`, …). The runner finds it under `plugins/*/skills/` and stops if the name matches zero or several.
- `<eval-ids>` is `all`, or a comma list whose items are single IDs or inclusive ranges (`0-4`), e.g. `1,3-5,9`. A single ID must exist in the suite; a range selects the existing IDs within its bounds and must match at least one. Otherwise the runner stops before running anything.
- `<model>` is an OpenRouter model ID (`z-ai/glm-5.3-flash`).
- `--runs N` (default 1) runs each eval N times, for noise studies and capability-flag evidence (which needs at least 10 runs per model configuration).
- `--variant NAME` passes NAME through to the harness's own `--variant` option, which selects the provider's reasoning effort for the model (for example `high`, or `minimal`). Omitted, the harness uses the model's default. The runner does not validate NAME; the harness and provider decide which values a model accepts. The variant is part of what was tested, so `batch.json` records it and the batch directory name carries it.

Runs are sequential. On completion the runner prints one line per run (eval, run number, status, cost) and the batch directory.

The runner is stdlib-only Python, executed from the repository root. Its tests replace the container and harness with a stub command, so they need no network, key, container runtime, or model. The event-stream parser is also tested against a trimmed stream recorded from the pinned harness version, so a harness bump that changes the stream's shape fails a test.

## Grading and recording

The runner does not grade. A frontier-model session grades each `completed` run with `skill-creator`'s grader against the eval's assertions, writing `grading.json` into the run directory in the standard `expectations` / `summary` shape. Grading an alternate-model run is the same act as grading a Claude run.

The pass rate is computed over `completed` runs only; `timeout` runs are reported beside it as a count; `harness_error` and `interrupted` runs appear in neither.

Graded results are recorded in the suite's `tested_with` list like any other run. Each entry names the exact OpenRouter model ID and the harness (`"harness": "opencode-ai@<version>"`), plus the variant (`"variant": "<name>"`) when the batch ran with one, since a model at a different reasoning effort is a different configuration. The field's schema belongs to the `linked-intent-dev` sub-HLD, which defines `tested_with`. A batch is recordable when:

- it has at least one `completed` run, and
- its `plugins/` tree ID is the `plugins/` tree of some commit in history (`git rev-parse <commit>:plugins`).

The second condition means a result always points at skill text anyone can check out. An author who tried a change on a dirty tree commits exactly what was tested, and the batch becomes recordable without a rerun. An author who amends or moves on to different text leaves the batch unrecordable, which is correct: it describes text that no longer exists.

## Permissions

Launching an autonomous coding agent with tool permissions pre-granted is what a cautious agent-permission policy blocks by default; Claude Code's auto-mode classifier blocks it. The repository therefore commits one allow rule for the runner's entry point in `.claude/settings.json`:

```
Bash(tools/alt-model-evals/run_eval.py:*)
```

A contributor working in this repository with Claude Code can then have their session run the runner without adding the rule themselves. The rule covers only the runner invocation. Reading and inspecting a run's outputs stays ordinary work under the session's normal permissions. The committed settings file is owned by `project-structure`, which records the rule as a cascade from this segment.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|---|---|---|---|
| Harness | opencode, run headless | A minimal in-repository tool loop (file tools only, path-jailed, no shell); Codex CLI (`codex exec`) or pi against an OpenAI-compatible endpoint; single-call prompts through `call-openrouter` | opencode has native OpenRouter support, a JSON event stream, and a working directory it stays in, and it gives the model the file and shell tools a real user's agent has. A minimal loop would be ours to maintain and less realistic: models reached for the shell in every trial run (`ls`, `find`, `git log`, `cp`, `rg`). Codex and pi are viable but have not been exercised here. Single-call prompting cannot test skills graded on the files the model edits, and it takes away the model's choice of what to read. |
| Sandbox | A container per run through the `docker` interface; `--no-container` as a warned opt-out | Throwaway `HOME` only; macOS `sandbox-exec`; a virtual machine per run | A throwaway home hides configuration but not the filesystem, so a model with a shell could read the checkout and its assertions. `sandbox-exec` is macOS-only and deprecated. A VM is heavier than the risk warrants. A container runtime is common among contributors who would run this at all, and the opt-out keeps the runner usable without one, with the weaker boundary stated. |
| Key exposure inside the sandbox | Key in the container environment; redacted from all outputs; a dedicated low-limit key advised | A per-batch key minted through OpenRouter's key-management API; a host-side proxy that adds the key to requests, so the container never holds it | Minting needs a separate provisioning key, and the proxy adds a moving part to own. Redaction plus a low-limit key bounds the loss to a small, revocable credit. Both alternatives stay available if that bound proves too loose. |
| Where runs execute | Locally, launched by a contributor or their agent session | A CI workflow | CI adds secrets management and workflow configuration the project does not otherwise need. A local runner plus one committed allow rule is enough, and it keeps the runs optional. |
| Harness version | Pinned, baked into the image, recorded with results | Globally installed `opencode`; always latest | A pin makes runs comparable over time. Tracking latest would change the executor silently between runs. |
| Container memory limit | 2 GiB, with a preflight check that the runtime has at least that much | 4 GB; no limit | Measured: opencode peaks near 1.2 GB on a real run. 4 GB exceeded colima's default VM outright, so a run died to a VM-wide out-of-memory kill rather than the container's own limit. The preflight turns that mid-run kill into a clear message before anything starts. |
| Timeout | 10 minutes by default, adjustable | 20 minutes (the Claude pilots' limit); no limit | 10 minutes clears the slowest recorded run with a margin, while a looping model stops costing time and money twice as fast. |
| Timeout status | Its own status, not graded, reported beside pass rates | Graded as a failure of every assertion; folded into `harness_error` | A loop is not a harness fault, and it is not an assertion-level failure either. Keeping it separate and visible shows what happened without distorting pass rates. |
| Interrupted runs | Their own status, neither graded nor reported | Recorded as `harness_error` or `timeout` | A person stopping the batch says nothing about the model or the skill; folding it into either status would distort what that status reports. |
| Capture location | A second container, with no network and no key, runs the git capture step | Host git hardened by configuration overrides (disable `core.fsmonitor`, hooks, external diff, textconv; restore the staged `.git/config`; reject a symlinked `.git`) | Git's set of configuration-driven program hooks is large and grows between versions, so a host-side blocklist would need auditing on every git release. Running capture where the model's planted configuration can only affect its own throwaway container needs no such list. |
| Skill staging | Copy the whole `plugins/` tree minus `evals/` and `*-workspace/` | Copy only the skill under test; mount the repository checkout | Skills cite siblings and other plugins by relative path, so a single-skill copy breaks those reads. Mounting the checkout would expose the eval's assertions and earlier runs. |
| Output layout | `skill-creator`'s per-eval shape, in the skill's gitignored workspace, plus `changes.patch` and `git-log.txt` | A separate results tree; committed results | The same grader and review tools work on Claude and alternate-model runs alike. The patch and log give a grader the baseline the stripped `.git` would otherwise take away. Raw runs are regenerable and stay out of version control. |
| Credential source | `OPENROUTER_API_KEY` in the environment | A per-user secrets file; the harness's auth store (`opencode auth login`); a key file in the repository | The environment variable is the harness-neutral convention, and how a contributor sets it stays their own business. A secrets-file convention is one person's setup, not the project's. The auth store writes the key to disk, and a repository key file risks a commit. |
| Permission model | One committed allow rule for the runner's entry point | Per-contributor settings; asking contributors to run it in their own shell | A committed rule makes the runner usable in any contributor's session without setup, and it records in the repository that this launch is intended. Per-contributor rules turn an optional helper into setup friction. |
| Identifying the skill text a result rests on | The git tree ID of `plugins/` as staged; recordable once some commit has that tree | Require a clean tree before a batch runs; record only the `HEAD` commit and a dirty flag; version-control-specific identifiers (a jj change or commit ID) | Requiring a clean tree forces a commit for every experiment with a skill edit. `HEAD` plus a dirty flag cannot tell which uncommitted text ran. The tree ID names the exact content, needs no commit, and lets a result become citable after the fact. It uses plain git, so contributors' own tools (jj or others) never change the runner's behavior. |
| Scratch location | `$XDG_CACHE_HOME/lid-alt-evals/` | The system temp directory | Container runtimes share the home directory with their VM by default on macOS and Windows; the macOS temp directory is not shared, so mounts from it come up empty. |
| Grading | Out of the runner; done by a frontier-model session with `skill-creator`'s grader | The runner calls a grader model itself | Grading shares one method with Claude runs, and the runner stays a thin wrapper. |
| Node placement | Top-level leaf under the HLD | A leaf under the `linked-intent-dev` sub-HLD; a section of `project-structure` | The runner serves every plugin's suites, so the lowest node that covers all of them is the root. It carries its own design decisions (harness, sandbox, permissions), which would bloat `project-structure`. |

## Open Questions & Future Decisions

### Resolved

1. ✅ Harness: opencode, pinned, in a container.
2. ✅ Runs are local and optional. No CI, no merge gate.
3. ✅ Results are recorded in `tested_with` with a `harness` field.

### Deferred

1. **Parallel runs.** Sequential runs are enough for single-eval checks. A noise study (10+ runs × several evals) would benefit from a bounded `--jobs N`.
2. **Baseline (without-skill) runs.** `skill-creator` pairs each with-skill run with a baseline. Alternate-model baselines would show whether a skill moves a non-Claude model at all, not just whether that model passes.
3. **A second harness.** Running the same model under two harnesses would separate model effects from harness effects. This matters for questions like how LID behaves inside tools that read `AGENTS.md` natively.
4. **A per-batch key.** OpenRouter's key-management API can create a key with a credit limit from a separate provisioning key. The runner could mint one per batch, pass only it into the containers, and delete it when the batch ends, so the contributor's own key never enters a container. This replaces the advice to keep a dedicated low-limit key.
5. **Egress restricted to OpenRouter, or a key-adding proxy.** Either closes the remaining key-exfiltration path outright.
