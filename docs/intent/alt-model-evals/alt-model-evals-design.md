# Alternate-Model Eval Runs

## Context and Design Philosophy

LID's behavioral eval suites (`plugins/*/skills/*/evals/evals.json`) run on Claude models, through `skill-creator` and `claude -p`. LID itself is meant for any model a user pairs it with, and its skills are written for an average executor, not a strong one. A suite's results say nothing about models it never ran on (HLD tenet *Design for the pair, not the model*). This segment owns the repository runner that executes those same suites on models from other providers, reached through OpenRouter, so the evidence behind LID's guidance can cover more than one model family.

Four principles shape the component:

- **Optional evidence, never a gate.** Alternate-model runs add evidence: a new `tested_with` entry, material for a capability-flag noise study, a signal that a skill's wording works only on strong models. They are never part of the merge gate (HLD § *Code and tests for LID*), and no contributor needs an OpenRouter account, a key, a container runtime, or the runner to contribute. The runner is a maintainer helper under *LID runs on the agent, not a runtime*: it may speed up evidence gathering, but nothing requires it.
- **Same eval, different executor.** A run uses the suite's own fixture files, its own prompt, and its own assertions, graded the same way as a Claude run. Only the model and the agent harness around it differ, so an alternate-model result can sit next to a Claude result and be compared directly.
- **The model sees the fixture and the skills, nothing else.** Each run executes inside a container that holds only the fixture project, a read-only copy of the plugins, and the harness. No instruction file, skill, plugin, credential, or file from the machine running it reaches the model. Neither does anything that reveals the expected answer: the eval's assertions, the eval's name, or earlier runs. This holds against a model that deliberately goes looking, not only against accidental leaks.
- **A real harness behind a thin wrapper.** The model works inside a shipping, open-source coding agent with ordinary file and shell tools, the kind of environment LID users actually run. The repository owns only the wrapper: fixture staging, the sandbox, invocation, and output capture. The harness's maintainers own the tool loop.

The runner and its Dockerfile are ordinary code and walk the standard arrow (`HLD → LLD → EARS → tests → code`). They ship in no plugin bundle and are never installed into a user's project.

## Harness

The harness is **opencode** (`opencode-ai` on npm), run headless as `opencode run`. It speaks to OpenRouter natively (`-m openrouter/<model-id>`), emits a JSON event stream (`--format json`) that serves as the run's transcript, gives the model read, write, edit, glob, grep, and bash tools, and works in whatever directory it is started in.

The harness version is **pinned** in one constant in the runner, baked into the container image at build time, and recorded with every run. It changes only by a deliberate edit, because a harness upgrade can change results as much as a model change can. A version bump rebuilds the image, confirms which instruction files the new version loads (below), and reruns a sample of earlier alternate-model runs before new results are compared with old ones. Past `tested_with` entries keep the harness they recorded.

Invocation flags:

- `--pure` — no external harness plugins.
- `--auto` — tool permissions are granted without prompting. A run is non-interactive, and everything the model can touch is disposable.
- `--format json` — the event stream on stdout.
- stdin is closed. `opencode run` reads piped stdin as extra message text and waits on it indefinitely when stdin is open.

The harness reads a configuration file generated by the runner, containing exactly: automatic updates off (`"autoupdate": false`), session sharing off (`"share": "disabled"`), and the OpenRouter provider's API key as the environment reference `{env:OPENROUTER_API_KEY}`.

The fixture's own instruction files (`AGENTS.md`, `CLAUDE.md`) load according to the harness's own rules for any project. That is what a real user of the harness gets. Which files a given harness version loads is confirmed when the pin changes, because the Claude runs load the fixture's `CLAUDE.md` and a difference there is a difference in what the executor was told.

## Sandbox

Each run executes in a container, started through the `docker` command-line interface. Any runtime that provides it works: colima, Docker Desktop, OrbStack, or Podman's Docker-compatible interface.

**Image.** `tools/alt-model-evals/Dockerfile` builds from a pinned Node base image and adds `git`, `ripgrep`, and `opencode-ai` at the pinned version. The runner tags the image with the harness version and a hash of the Dockerfile, and builds it on first use when no image with that tag exists.

**Container.** The runner starts one container per run with:

- the fixture project mounted read-write at `/work/project`, which is the working directory;
- the staged plugins mounted read-only at `/work/plugins`;
- the generated harness configuration mounted read-only at `/work/opencode.json`, outside the project, and pointed at by `OPENCODE_CONFIG`;
- a private, in-memory home directory (`/home/eval`) and `/tmp`, and an otherwise read-only root filesystem;
- the host user's UID and GID, so files the model writes are owned by the person running the runner, with generated one-line `/etc/passwd` and `/etc/group` files mounted read-only so tools that look up the current user (Node's `os.userInfo()` among them) find an entry;
- all Linux capabilities dropped, privilege escalation disabled, a 2 GiB memory limit, and a 512-process limit;
- an environment holding only the OpenRouter key, the home directory, a git author and committer identity (so a skill that commits works), and locale basics;
- network egress, which the harness needs to reach OpenRouter.

The harness is invoked with a direct argument list, never through a shell. Nothing else from the host is mounted. The model cannot read the repository checkout, the invoking user's home directory, or other runs, even with a shell and absolute paths.

**Capture stays in the sandbox.** Everything in the project directory, `.git/` included, was writable by the model, so the host treats that directory as untrusted after the harness starts. Git in particular executes programs named in a repository's own configuration and attributes (`core.fsmonitor`, filter drivers, diff drivers, hooks), and a `.git` that is a symbolic link or a `gitdir:` file can point git at a directory outside the project. The runner therefore never runs git on the host in the project directory once the harness has started. The change patch and git log are produced by a second, short-lived container from the same image and with the same hardening, which mounts the project read-write and an empty output directory, has no network and no key, and runs a fixed capture step: remove a stale `.git/index.lock`, stage everything into a temporary index, write the patch against the fixture commit, and write the log. Anything the model planted in `.git/` can fire only inside that throwaway container; the worst it can do is falsify its own run's patch, which the model could already influence by editing files. On the host, the runner only copies the project — preserving symbolic links as links without following them, and skipping FIFOs, sockets, and device files — and redacts the copy.

**Memory.** The harness itself dominates memory use: opencode peaked at about 1.2 GB resident during a five-minute `lid-coach` run, and a run's in-memory home and `/tmp` count against the same budget. The 2 GiB limit leaves headroom above that peak while still stopping a runaway process. On macOS and Windows the containers run inside a VM whose memory is fixed when the runtime starts, and colima's default is 2 GiB, shared with every other container on the machine. A VM with less total memory than the container's limit cannot run it at all, so the runner checks the runtime's total memory before staging anything and stops with the two numbers when it falls short. A roster run with lanes (see *Rosters*) needs that much per lane. The check catches only that impossible case: a VM that clears it can still run out mid-run when other containers share it, and that surfaces as a `harness_error` with exit code 137. About 4 GiB for the VM is the practical recommendation.

**What the model can still reach.** The container has to hold the OpenRouter key so the harness can call the API, and the bash tool can read it (`echo $OPENROUTER_API_KEY`). Network egress is open. A model could therefore send the key somewhere. Two measures bound this. First, the runner redacts every literal occurrence of the key from the captured outputs (below); a copy the model deliberately encodes (base64, split across lines) is not caught. Second, contributors are advised to run evals with a dedicated OpenRouter key with a low credit limit, so a leaked key is cheap to lose and revoke.

**Running without a container.** When no `docker` interface is reachable, the runner stops and says so. `--no-container` runs the harness directly on the host, through `npx`, with a throwaway `HOME` and `XDG_*` root and an environment reduced to an allowlist (the key, `PATH`, the throwaway home, git identity, locale). This hides the user's configuration and credentials, but it is not a filesystem boundary: a model with a shell can read any file the user can. The runner prints that warning before starting and records the mode in the batch record. The npm cache stays at the user's own location so each run does not download the harness again.

### Credentials

The OpenRouter key comes from `OPENROUTER_API_KEY` in the environment, the name the harness and most OpenRouter clients already use. With no key, the runner stops before staging anything and names the variable. The price lookup (see *Cost*) reads a public list and is sent no key.

The runner never puts the key on disk or in a process listing: not in the generated configuration, not in the arguments of any process it starts (`docker` receives it by name and inherits the value). The capture container does not receive it at all. Before a run's outputs are written to the workspace, every captured regular file — the transcript, stderr, the final response, the change patch, the git log, and every file in the captured project — has each byte-for-byte occurrence of the key replaced with `[REDACTED]`. Redaction treats every file as bytes rather than guessing which files are text, leaves symbolic links alone, and keeps each file's mode.

## Staging a run

For each run, the runner creates a scratch directory with a random name under `$XDG_CACHE_HOME/lid-alt-evals/` (`~/.cache/lid-alt-evals/` by default). The location sits under the user's home directory because container runtimes share the home directory with their VM by default — colima and Docker Desktop on macOS, Docker's WSL integration on Windows — while the system temp directory (`/var/folders/…` on macOS) is often not shared, and a mount from it would come up empty inside the container. The directory's parent path is never visible inside the container.

```
~/.cache/lid-alt-evals/<random>/
  project/        ← the eval's fixture files, as a fresh git repository with one commit
  plugins/        ← a copy of the invocation's plugins/ snapshot
  opencode.json   ← the generated harness configuration
```

- **Fixture.** Each entry in the eval's `files` list is written under `project/` at its `path`, with its content exactly as given. A path that is absolute, contains a `..` segment, or begins with a `.git` segment is a malformed suite: the runner checks every selected eval's paths before running anything, and stops if any is malformed. The directory is initialized as a git repository and committed once with a fixed identity and the message `fixture`, so skills that read history or diff against `HEAD` behave as in a real project. An eval with no files gets an empty commit, with no placeholder file.
- **Skills.** The whole `plugins/` tree is copied, mirroring its repository layout, because skills reach outside their own directory: `lid-coach` reads a sibling skill's `references/capability-flags.md`, `update-lid` reads its plugin's `plugin.json` for the version, and `map-codebase` links into another plugin by relative path. The copy excludes every `evals/` directory and every `*-workspace/` directory, at any depth, so no assertion and no earlier run output is reachable. The runner takes this copy once, at the start of an invocation, as a snapshot in its own scratch directory, and computes the tree ID `batch.json` records (see *Outputs*) at the same moment; every run of every batch the invocation starts stages its `plugins/` from that snapshot. The snapshot holds exactly the files that tree ID covers (tracked files, and untracked ones git does not ignore), minus the excluded directories, with symbolic links kept as links, so the text a run sees is the text its tree ID names. The runner reads every suite's `evals.json` the invocation needs at the same moment, so each batch's prompts, fixtures, and assertions are also those of the invocation's start. Edits to the repository's `plugins/` while a long batch or roster runs therefore reach no run, and every run matches its recorded tree. The snapshot is removed when the invocation ends.
- **Skill loading.** `opencode.json` lists the staged `plugins/` directory under `skills.paths`, so opencode's own skill tool discovers every staged skill, as it would for a user with the plugins installed. The run loads the skill through that tool, which delivers `SKILL.md` whole. Reading `SKILL.md` as a file would go through opencode's file-read tool instead, which cuts every line longer than 2,000 characters and caps each read at 50 KB. That is not how a user's agent receives a skill, so a run that read it that way would test a skill the user never sees. Files a skill points to (its `references/`, sibling skills) are still read as files, as they are in real use.
- **No side calls.** `opencode.json` disables opencode's `title` agent. It generates a session title with a separate "small model" (`google/gemini-3.8-flash` through OpenRouter), which adds requests to a second model that a headless run has no use for. With it disabled, every request in a run goes to the model under test. Compaction of long conversations is unaffected, since it uses the main model.

Paths inside the container (`/work/project`, `/work/plugins`) are fixed and neutral. The eval's name appears nowhere the model can see.

### The run prompt

The model receives one message, built from a fixed template shared by every run:

1. It is executing one eval run of an agent skill; the current directory is the project root and the entire repository.
2. Load the skill named `<skill>` with your skill tool, and read any references it directs you to. Sibling skills live under `/work/plugins/`.
3. The user's request, quoted verbatim from the eval's `prompt`. Execute it per the skill against the current directory, making any file changes yourself.
4. The run is non-interactive: where the skill would ask the user, take the skill's stated default and state in the final response which defaults were taken. Today's date is the run date.
5. The final message is the exact user-facing response and nothing else.

An eval with a scripted `follow_up` replaces line 4 with: the user will read the final message and reply; where the skill directs you to ask the user, ask in your final message and stop, without answering for them. A real user is about to answer, so taking a default would put words in their mouth, and it would contradict evals that check whether the model asks (a decision-doc offer, for instance). Asked to state which defaults it took, a model also narrates choices it was told not to raise.

This follows the prompt the Claude pilot runs use, with two differences: it names an "agent skill" rather than a Claude Code skill, and it loads the skill through the harness's own skill mechanism rather than by file path. `<skill>` is the `name` in the skill's frontmatter, falling back to its directory name. In `--no-container` mode the plugin path, in the prompt and in `skills.paths`, is the scratch directory's `plugins/`.

## Run lifecycle and status

Each run has two limits on the harness, both measured from the moment the harness starts, so staging and a first-use image build do not count against them:

- an **inactivity limit**, 10 minutes by default and set with `--idle-timeout`: the run is stopped when the harness writes nothing to its event stream for that long;
- a **run limit**, 30 minutes by default and set with `--timeout`: the run is stopped when it has lasted that long, however busy it is.

The inactivity limit catches a stalled host or stream. opencode writes a reasoning block to the stream only when the block ends, so a model thinking at length is silent: the longest silence in a completed run on record is about five and a half minutes (`tencent/hy4`), and the limit leaves room for twice that. The run limit bounds a model that keeps working: a model that runs past a phase stop can go on well beyond 10 minutes while emitting events every minute or two, and only the run limit stops it. Most runs finish in two to five minutes.

A run ends in exactly one status:

- **`completed`** — the harness exited zero and emitted no top-level `error` event (a line of the event stream whose own `type` is `error`). A tool call that failed and that the model worked around is model behavior, not a harness error. Graded. A completed run with an empty final message is still graded, and its response assertions fail.
- **`harness_error`** — the harness exited non-zero or emitted a top-level `error` event (a rejected key, an unknown model, a model without tool support, an API failure the harness gave up retrying). Not graded: it says nothing about the skill.
- **`timeout`** — the run reached its inactivity limit or its run limit and was stopped; `timing.json` records which. Not graded and not recorded: a stopped run leaves no final answer to grade. An inactivity stop usually means a stalled host or stream, a transient failure like a harness error; a run-limit stop means the model was still working. Either way the run is repeated when its outcome could change a result (the `linked-intent-dev` sub-HLD's *Capability Flags* evidence bar).
- **`interrupted`** — the person running the batch stopped it (Ctrl-C, a termination signal, a closed terminal), or the runner stopped it because of a runner failure. An interrupt during a follow-up turn makes the whole run `interrupted`. Not graded and not reported: it says nothing about the model or the skill.

Outputs are captured for every status, including partial project state from errored, timed-out, and interrupted runs.

On timeout, on an interrupt, and on any runner failure, the runner stops the container (or, without a container, the harness's whole process group) with a termination signal, kills whatever remains after 10 seconds, captures what exists (the capture step clears any stale git lock the kill left behind), and removes the scratch directory. After two consecutive `harness_error` runs anywhere in the batch, the runner stops the batch: a bad key or model ID would otherwise fail every remaining run. In a roster, it also stops that model's other batches, whether or not the batch it happened in had runs left, since whatever failed twice in one batch would fail them too: none of that model's batches starts another run, its runs already in progress finish, and other models carry on. A runner failure is an error in the runner's own steps (staging, the capture container, writing outputs), not in the harness: a harness container that fails to start is a non-zero harness exit, recorded as `harness_error`. In a roster, a runner failure in one lane stops every lane, and every run it stops, in the failing lane or another, ends `interrupted`.

### Follow-up turns

An eval may carry a scripted second turn (`follow_up`, see the `linked-intent-dev` sub-HLD's eval conventions) for behavior a skill reserves for later turns. When the first turn completes, the runner starts the harness a second time with the follow-up prompt and opencode's `--continue`, so the model answers in the same session with its first turn in context. The second turn has its own limits and its own status. When the first turn does not complete, the follow-up is not run and its status is `skipped`. The run's own status is the first turn's, except that an interrupt during either turn makes the run `interrupted`: the person stopped it, so grading its unfinished second turn would count their stop against the model.

Session state must outlive the first harness process. The container's home directory is an in-memory filesystem discarded when the container exits, so the runner points opencode's data directory (`XDG_DATA_HOME`) at a `state/` folder in the run's scratch directory, mounted read-write at `/work/state`; without a container, the run's private home already persists across both turns. Either way the state is deleted with the scratch directory. Project changes are captured after the last turn and, when a follow-up runs, also after the first turn, so a grader can tell which turn made a change: whether a file was written before the user's second message, for instance.

## Outputs

Runs land in the skill's gitignored workspace, beside the Claude runs, in the per-eval shape `skill-creator`'s grader reads:

```
plugins/<plugin>/skills/<skill>-workspace/alt-model-<YYYY-MM-DD>-<model-slug>/
  batch.json
  eval-<id>-<name>/
    eval_metadata.json        ← eval_id, eval_name, prompt, assertions (copied from evals.json as-is)
    with_skill/run-<n>/
      events.jsonl            ← the harness's JSON event stream: the transcript
      response.md             ← the model's final text message
      timing.json
      stderr.log
      changes.patch           ← every difference from the fixture commit, untracked files included
      changes1.patch          ← the same, as of the end of the first turn (only when a follow-up ran)
      git-log.txt             ← the project's history, including any commits the model made
      project/                ← the fixture directory's final state, without .git
```

- Runs within a batch go eval by eval, in ascending ID order, all runs of one eval before the next.
- `<model-slug>` is the OpenRouter model ID with every character outside `[A-Za-z0-9._-]` replaced by `_`. `<name>` is the eval's `eval_name`, sanitized the same way. `<YYYY-MM-DD>` is the batch's start date. Runs are numbered from 1.
- A second batch for the same model on the same day gets a numeric suffix. The runner claims the directory by creating it, so two concurrent batches cannot take the same one.
- A cost probe's batch (see *Cost*) is named `cost-probe-<YYYY-MM-DD>-<model-slug>` instead, with the same numeric suffix rule, so a match on `alt-model-*` never picks it up. `probe` in its `batch.json` is what marks it as a probe.
- `project/` preserves symbolic links as links and keeps file modes, so assertions about symlinks and executables can be graded. FIFOs, sockets, and device files are not copied.
- `response.md` is the text of the last event of type `text` in the stream. Each such event carries one complete text part (opencode emits a part when it finishes, not as streamed fragments), so the last one is the model's final message. Reasoning and tool output never count as the response. `git-log.txt` is `git log --stat` from the final `HEAD`.
- `changes.patch` and `git-log.txt` let a grader check that a run changed nothing, or exactly what it changed, without the stripped `.git`.

`timing.json` records: `model` (the OpenRouter ID), `harness` (`opencode-ai@<version>`), `status`, `duration_ms`, `total_cost_usd` and token counts summed from the event stream (`null` when the stream carries none), the number of tool calls, `exit_code`, `error_message`, `timeout_limit`, which names the limit that stopped a `timeout` run (`inactivity` or `run`) and is `null` for every other status, and `priced_cost_usd` (see *Cost*; `null` when the runner has no prices). A follow-up turn's record carries the same fields.

`batch.json` records the skill, eval IDs, model, effort, variant, harness, sandbox mode (`container` or `none`), the run limit and the inactivity limit, run count, the repository's `HEAD` commit, the **git tree ID of `plugins/` as staged**, whether that tree matches `HEAD`'s, the batch state (`running`, then `complete` or `aborted`), and why an aborted batch stopped (`stop_reason`: `harness_errors`, `interrupted`, `max_cost`, or `runner_error`; `null` otherwise). A batch is `aborted` only when it left runs it would have made unstarted; a stop that comes after its last run leaves it `complete`. A batch records the first stop that reached it, except that an interrupt, whenever it comes, is the reason recorded. It also records the cost settings: the model's per-token prices and when they were read (`prices`, `null` without them), the cost cap (`max_cost`, `null` without one), and whether the batch is a cost probe (`probe`). A batch a roster started records the roster preset and a roster ID shared by every batch that invocation started (`roster`, `null` for a single batch).

The tree ID identifies exactly the skill text a batch ran against, whether or not it was committed. The runner computes it with a temporary git index over the on-disk `plugins/` directory (tracked and untracked files, gitignored ones excluded), leaving the repository's own index, working tree, and history untouched. Running on uncommitted skill edits is normal — it is how a skill change is tried out — and the runner never refuses it.

## Invocation

```
tools/alt-model-evals/run_eval.py <skill> <eval-ids> <model> [--runs N] [options]
tools/alt-model-evals/run_eval.py --roster <preset> <model> [<model> ...] [--lanes N] [options]

options: [--estimate] [--max-cost USD] [--timeout SECONDS] [--idle-timeout SECONDS]
         [--effort LEVEL] [--variant NAME] [--no-container]
```

The first form runs one batch: some evals of one suite, for one model. The second runs a roster: a preset's batches across several suites, for each model named (see *Rosters*).

- `<skill>` is a skill directory name (`lid-coach`, `update-lid`, `arrow-maintenance`, `map-codebase`, …). The runner finds it under `plugins/*/skills/` and stops if the name matches zero or several.
- `<eval-ids>` is `all`, or a comma list whose items are single IDs or inclusive ranges (`0-4`), e.g. `1,3-5,9`. A single ID must exist in the suite; a range selects the existing IDs within its bounds and must match at least one. Otherwise the runner stops before running anything.
- `<model>` is an OpenRouter model ID (`z-ai/glm-5.3-flash`).
- `--runs N` (default 1) runs each eval N times, for noise studies and capability-flag evidence (which needs at least 10 runs per model configuration). It applies to the single-batch form only; a roster preset sets its own run counts.
- `--roster <preset>` names the roster to run; the positional arguments are then one or more OpenRouter model IDs. `--lanes N` (default 1) runs up to N of the roster's batches at once.
- `--estimate` runs a small cost probe in place of the batch or roster and prints the projected cost; `--max-cost USD` stops starting runs of a model once its spend reaches USD (both under *Cost*).
- In a roster, `--timeout`, `--idle-timeout`, `--effort`, `--variant`, and `--no-container` apply to every batch, cost probes included.
- The runner stops before running anything, naming the problem, when `--runs` is given with `--roster`, `--lanes` without `--roster`, a model ID is named twice, `--max-cost` is not above zero, or `--lanes` is below one. A roster checks the eval IDs and fixture paths of all its batches, and every model's OpenRouter entry (see *Cost*), before any batch starts.
- `--timeout SECONDS` (default 1800) sets the run limit and `--idle-timeout SECONDS` (default 600) the inactivity limit, described under *Run lifecycle and status*.
- `--effort LEVEL` (default `medium`) pins the model's reasoning effort, written into the run's `opencode.json` as the model's `reasoning.effort` option for OpenRouter. `medium` is the effort LID's capability evidence is measured at (see the `linked-intent-dev` sub-HLD's *Capability Flags*). It is pinned rather than left to the model because OpenRouter's defaults differ by model family (no reasoning for Claude 4.x, `medium` for GPT and Gemini, `max` for GLM 5.3 and Kimi K3), and effort moves results as much as the model does. `--effort default` sends no effort, so the model's own default applies.
- `--variant NAME` passes NAME through to the harness's own `--variant` option, for provider-specific settings `--effort` does not cover. The runner does not validate NAME.

Within a batch, runs are sequential. On completion the runner prints one line per run (eval, run number, status, priced cost), the batch's total priced cost, and the batch directory. A roster prints a one-line note as each batch ends, and when the roster ends prints every batch's summary once, then each model's total, then any planned batches that never started. An interrupt, a cost cap, or a harness-error stop still prints the summary for everything that ran.

The runner exits zero when every batch it ran is complete, 130 when an interrupt stopped it, and 1 when any batch aborted for another reason or a roster left a planned batch unstarted. With `--estimate`, it exits 1 when any model got no projection.

The runner is stdlib-only Python, executed from the repository root. Its tests replace the container and harness with a stub command, and OpenRouter's model list with a local file, so they need no network, key, container runtime, or model. The event-stream parser is also tested against a trimmed stream recorded from the pinned harness version, so a harness bump that changes the stream's shape fails a test.

### Observed reasoning

Asking for an effort does not guarantee the model reasons: a provider can ignore the setting, and `claude-sonnet-4.5` through OpenRouter at `high` produced about 80 reasoning tokens per run. Each run's `timing.json` already records its reasoning tokens. The run summary reports the batch's median reasoning tokens, and when an effort was requested but that median is under 500 tokens it prints a warning, so a batch that did not reason is visible before anyone grades it.

## Rosters

A roster is a named set of batches across several suites, run together for one or more models. The runner's presets live beside it in `tools/alt-model-evals/rosters.json`; it defines one, `capability`: the runs behind a model's capability-flag row and its `tested_with` entries.

| Batch | Suite | Evals | Runs of each eval |
|---|---|---|---|
| 1 | `linked-intent-dev` | 0, 1 | 10 |
| 2 | `linked-intent-dev` | 2, 3 | 10 |
| 3 | `lid-coach` | 10, 11 | 10 |
| 4 | `lid-coach` | 15, 16 | 10 |
| 5 | `update-lid` | all | 1 |

Its cost probe (see *Cost*) is one run of `linked-intent-dev` eval 0 and one run of `lid-coach` eval 15.

- The core and coach evals are the test projects the `linked-intent-dev` sub-HLD's *Capability Flags* names for its flags and tendency, at its 10 runs per project; the `update-lid` batch supplies that suite's `tested_with` entry. When the sub-HLD changes which projects stand behind a flag, the preset changes with it.
- The preset splits suites into batches so lanes can share the work, and never splits one eval across batches, so all of a model's runs of one eval come from one batch. It names its evals by ID, not by range, so an eval missing from a suite fails the roster's checks instead of being skipped.
- A roster runs whatever `plugins/` tree the repository holds. It does not prepare the capability-stripped copy that capability-flag evidence needs; that copy is made and checked by hand, as the sub-HLD describes.
- With several models, the runner queues batches interleaved by model (every model's first batch, then every model's second, and so on), so all the models progress together and a roster stopped partway leaves them with comparable coverage.
- `--lanes N` keeps N batches running while that many are queued, starting the next as soon as one ends. A batch starts when its first run is about to start, once its model's stop checks pass; a batch that never starts claims no directory. Each batch is an ordinary batch, with its own directory, `batch.json`, sequential runs, and two-harness-error rule. Each lane holds one container at a time, so the memory preflight requires the container's memory limit times N or the number of batches queued, whichever is smaller. An interrupt stops every lane, and each lane's current run ends `interrupted`.

## Cost

The person running a batch pays for it, and spend on the same evals varies more than tenfold across models, mostly with how much a model reasons. The runner prices every run from OpenRouter's published prices, can project a batch's or roster's cost from a small paid probe before committing to it, and can cap each model's spend.

**Prices.** Before staging anything, the runner reads the model's entry from OpenRouter's public model list (`https://openrouter.ai/api/v1/models`). The entry gives per-token prices for prompt tokens, completion tokens, internal reasoning, cache reads, and cache writes; `batch.json` records them with the time they were read, so a cost can be recomputed later at the prices in force. Two things in the list stop the runner before staging: no entry for the model ID, since OpenRouter does not serve that ID; and an entry whose supported parameters lack tool calling, since the harness cannot work without tools and every run would fail. In a roster, any model that fails either check stops the whole invocation before anything runs. When the list cannot be fetched or parsed, or a model's entry lists no prompt or no completion price, the runner warns and runs that model without prices, unless `--estimate` or `--max-cost` needs them, in which case it stops.

**Priced cost.** A turn's priced cost is its uncached input tokens at the prompt price, plus its cache-read tokens at the cache-read price, its cache-write tokens at the cache-write price, its output tokens at the completion price, and its reasoning tokens at the internal-reasoning price. The harness reports these five counts separately, with no token in two of them, so each token is priced once. A price the entry lists is used as listed, zero included. A price it does not list falls back to the completion price for reasoning and to the prompt price for cache reads and writes, which errs high, the safe direction for an estimate or a cap. A turn the stream reports no token counts for costs zero. `timing.json` records `priced_cost_usd` for the first turn and, in its own record, for a follow-up turn, beside the harness's own `total_cost_usd`, which is kept as data; a run's priced cost is the sum of its turns'. Every turn that ran is priced, whatever its status, since a turn cut short was still paid for. Summaries, the estimate, and the cap use priced cost. Without prices, a summary shows the harness's figures, totaled over the runs that report one, labeled as the harness's and with a count of the runs that reported none.

**Estimate.** `--estimate` runs a probe in place of the batch or roster, prints a projection, and stops. Before the probe starts, the runner makes every check it would make before the batch or roster itself (skills, eval selectors, fixture paths, and every model's entry), so an estimate also shows the roster would start. A roster's probe is its preset's probe runs for each model, as one probe batch per suite, each in that suite's workspace and recording the roster; a single batch's probe is one run of its lowest selected eval. Probe runs are ordinary runs, with the same staging, sandbox, limits, and follow-up turn, and they share the roster's lanes. For each model the runner prints its prices, what its probe cost, its projected cost (the mean priced cost of its probe runs times the number of runs the batch or roster would make), and its projected run time (their mean elapsed time, from staging through capture, times those runs). For the invocation as a whole, it prints a projected wall-clock time, from placing each queued batch, at its model's mean elapsed time per probe run, into the lanes in queue order. A model gets a projection only when every one of its planned probe runs completed, follow-up turn included; otherwise the runner reports each probe run's status and error message instead, and a probe run that never started as not started. An interrupt during the probe still prints the projections of models whose probes finished.

**Cap.** `--max-cost USD` limits each model's priced spend within one invocation, across all of its batches and lanes. It applies to whatever the invocation runs, a probe included. Before starting a run, the runner adds up the priced cost of every turn of that model that has finished so far, whatever its status; once the total has reached the cap, no further run of that model starts, and each of its batches with runs left ends `aborted` with stop reason `max_cost`. Cost is known only when a turn ends, so a run in progress always finishes, and spend can pass the cap by up to one run per lane. Other models' batches carry on.

## Grading and recording

The runner does not grade. A frontier-model session grades each `completed` run with `skill-creator`'s grader against the eval's assertions, writing `grading.json` into the run directory in the standard `expectations` / `summary` shape. Grading an alternate-model run is the same act as grading a Claude run.

A cost probe's batch (one whose `batch.json` sets `probe`) is never graded or recorded: it exists to price a roster and to show the model works in the harness at all.

The pass rate is computed over `completed` runs only; `timeout`, `harness_error`, and `interrupted` runs appear in neither the pass rate nor the `tested_with` entry.

Graded results are recorded in the suite's `tested_with` list like any other run. Each entry names the exact OpenRouter model ID and the harness (`"harness": "opencode-ai@<version>"`), plus the effort (`"effort": "medium"`) and the variant when one was given, since a model at a different reasoning effort is a different configuration. The field's schema belongs to the `linked-intent-dev` sub-HLD, which defines `tested_with`. A batch is recordable when:

- it has at least one `completed` run, and
- its `plugins/` tree ID is the `plugins/` tree of some commit in history (`git rev-parse <commit>:plugins`), or, for a run producing capability-flag evidence, that commit's tree with the capability subsystem removed and checked as the `linked-intent-dev` sub-HLD's *Capability Flags* describes. The model is given the staged copy, so that check's search skips the `evals/` and `*-workspace/` directories staging leaves out, while its diff covers the whole recorded tree.

The second condition means a result always points at skill text anyone can check out, or, for capability-flag evidence, at a commit plus the sub-HLD's rule for what was removed from it. An author who tried a change on a dirty tree commits exactly what was tested, and the batch becomes recordable without a rerun. An author who amends or moves on to different text leaves the batch unrecordable, which is correct: it describes text that no longer exists.

## Permissions

Launching an autonomous coding agent with tool permissions pre-granted is what a cautious agent-permission policy blocks by default; Claude Code's auto-mode classifier blocks it. The repository therefore commits one allow rule for the runner's entry point in `.claude/settings.json`:

```
Bash(tools/alt-model-evals/run_eval.py:*)
```

A contributor working in this repository with Claude Code can then have their session run the runner without adding the rule themselves. The rule covers only the runner invocation. Reading and inspecting a run's outputs stays ordinary work under the session's normal permissions. The committed settings file is owned by `project-structure`, which records the rule as a cascade from this segment.

## Decisions & Alternatives

| Decision | Chosen | Alternatives Considered | Rationale |
|---|---|---|---|
| Loading the skill | opencode's native skill tool, with the staged `plugins/` listed in `skills.paths` | Tell the model to read `SKILL.md` by path; place the skill in the project's `.claude/skills/` | Reading by path goes through opencode's file-read tool, which silently cuts lines longer than 2,000 characters. Measured: `claude-sonnet-4-5` never saw the end of a 3,136-character principle line in `lid-coach`, and its results diverged sharply from `claude -p`. A project-local `.claude/skills/` would put the skill inside the project under review and inside its captured diff. |
| Harness | opencode, run headless | A minimal in-repository tool loop (file tools only, path-jailed, no shell); Codex CLI (`codex exec`) or pi against an OpenAI-compatible endpoint; single-call prompts through `call-openrouter` | opencode has native OpenRouter support, a JSON event stream, and a working directory it stays in, and it gives the model the file and shell tools a real user's agent has. A minimal loop would be ours to maintain and less realistic: models reached for the shell in every trial run (`ls`, `find`, `git log`, `cp`, `rg`). Codex and pi are viable but have not been exercised here. Single-call prompting cannot test skills graded on the files the model edits, and it takes away the model's choice of what to read. |
| Sandbox | A container per run through the `docker` interface; `--no-container` as a warned opt-out | Throwaway `HOME` only; macOS `sandbox-exec`; a virtual machine per run | A throwaway home hides configuration but not the filesystem, so a model with a shell could read the checkout and its assertions. `sandbox-exec` is macOS-only and deprecated. A VM is heavier than the risk warrants. A container runtime is common among contributors who would run this at all, and the opt-out keeps the runner usable without one, with the weaker boundary stated. |
| Key exposure inside the sandbox | Key in the container environment; redacted from all outputs; a dedicated low-limit key advised | A per-batch key minted through OpenRouter's key-management API; a host-side proxy that adds the key to requests, so the container never holds it | Minting needs a separate provisioning key, and the proxy adds a moving part to own. Redaction plus a low-limit key bounds the loss to a small, revocable credit. Both alternatives stay available if that bound proves too loose. |
| Where runs execute | Locally, launched by a contributor or their agent session | A CI workflow | CI adds secrets management and workflow configuration the project does not otherwise need. A local runner plus one committed allow rule is enough, and it keeps the runs optional. |
| Harness version | Pinned, baked into the image, recorded with results | Globally installed `opencode`; always latest | A pin makes runs comparable over time. Tracking latest would change the executor silently between runs. |
| Container memory limit | 2 GiB, with a preflight check that the runtime has at least that much | 4 GB; no limit | Measured: opencode peaks near 1.2 GB on a real run. 4 GB exceeded colima's default VM outright, so a run died to a VM-wide out-of-memory kill rather than the container's own limit. The preflight turns that mid-run kill into a clear message before anything starts. |
| Run limits | A 10-minute inactivity limit and a 30-minute run limit, both adjustable | One wall-clock limit (10 minutes, or 20, the Claude pilots' limit); no limit; a cap on the number of steps | Models differ in how long they work and how long they go quiet. Completed runs went silent for up to about five and a half minutes while reasoning (`tencent/hy4`), and a model running past a phase stop kept working beyond 10 minutes while emitting events every one to three minutes (`minimax/minimax-m3.1-flash`, 21 runs stopped by a 10-minute limit). One limit either stops such runs before they answer or waits just as long for a dead stream. The inactivity limit catches a stalled host or stream no later than a single 10-minute limit did, and the run limit bounds what a model that keeps working can cost. A step cap depends on the harness counting steps and says nothing about a stalled stream. Runs measured under a single 10-minute limit lost long-working runs that the run limit now lets finish; only configurations that overran are affected, and their evidence notes say so. |
| Timeout status | Its own status, neither graded nor recorded | Graded as a failure of every assertion; reported beside the pass rate as a count; folded into `harness_error` | A timeout is not an assertion-level failure, and a single one cannot tell a model that loops from a slow host serving it; the same model runs on other hosts, so the record keeps what the model does, and a model that truly loops keeps timing out when the run is repeated. Its own status still tells the person running the batch a slow run from a broken one, and recording which limit stopped the run keeps a stalled host apart from a model that kept working. |
| Interrupted runs | Their own status, neither graded nor reported | Recorded as `harness_error` or `timeout` | A person stopping the batch says nothing about the model or the skill; folding it into either status would distort what that status reports. |
| Capture location | A second container, with no network and no key, runs the git capture step | Host git hardened by configuration overrides (disable `core.fsmonitor`, hooks, external diff, textconv; restore the staged `.git/config`; reject a symlinked `.git`) | Git's set of configuration-driven program hooks is large and grows between versions, so a host-side blocklist would need auditing on every git release. Running capture where the model's planted configuration can only affect its own throwaway container needs no such list. |
| Skill staging | Copy the whole `plugins/` tree minus `evals/` and `*-workspace/` | Copy only the skill under test; mount the repository checkout | Skills cite siblings and other plugins by relative path, so a single-skill copy breaks those reads. Mounting the checkout would expose the eval's assertions and earlier runs. |
| Output layout | `skill-creator`'s per-eval shape, in the skill's gitignored workspace, plus `changes.patch` and `git-log.txt` | A separate results tree; committed results | The same grader and review tools work on Claude and alternate-model runs alike. The patch and log give a grader the baseline the stripped `.git` would otherwise take away. Raw runs are regenerable and stay out of version control. |
| Credential source | `OPENROUTER_API_KEY` in the environment | A per-user secrets file; the harness's auth store (`opencode auth login`); a key file in the repository | The environment variable is the harness-neutral convention, and how a contributor sets it stays their own business. A secrets-file convention is one person's setup, not the project's. The auth store writes the key to disk, and a repository key file risks a commit. |
| Permission model | One committed allow rule for the runner's entry point | Per-contributor settings; asking contributors to run it in their own shell | A committed rule makes the runner usable in any contributor's session without setup, and it records in the repository that this launch is intended. Per-contributor rules turn an optional helper into setup friction. |
| Identifying the skill text a result rests on | The git tree ID of `plugins/` as staged; recordable once some commit has that tree, or, for capability-flag evidence, once the copy's source commit is in history | Require a clean tree before a batch runs; record only the `HEAD` commit and a dirty flag; version-control-specific identifiers (a jj change or commit ID) | Requiring a clean tree forces a commit for every experiment with a skill edit. `HEAD` plus a dirty flag cannot tell which uncommitted text ran. The tree ID names the exact content, needs no commit, and lets a result become citable after the fact. It uses plain git, so contributors' own tools (jj or others) never change the runner's behavior. Capability-flag evidence is the exception because its uncommitted text is known: the copy differs from its source commit only by the capability subsystem's removal, which a search and a diff check before the run (`linked-intent-dev` sub-HLD, *Capability Flags*). Committing every stripped copy would add a ref to the repository each evidence round to name text the commit and that rule already name. |
| Scratch location | `$XDG_CACHE_HOME/lid-alt-evals/` | The system temp directory | Container runtimes share the home directory with their VM by default on macOS and Windows; the macOS temp directory is not shared, so mounts from it come up empty. |
| Cost source | OpenRouter's published per-token prices times each turn's token counts, for every run; the harness's figure kept as data | The harness's figure, priced only when it reports none; OpenRouter's billed cost per request | The harness prices runs from its own model catalog, which lags new releases: across one batch of a newly released model it reported $0 for some turns and a real figure for others, so a fallback rule would mix two sources within one batch. Published prices times tokens came within about 7% of the key's recorded spend across a 282-run roster. Billed cost per request would be exact, but OpenRouter reports it by generation ID, and the harness's event stream carries none. |
| Estimating a roster's cost | A paid probe of real runs, projected by mean cost per run | Earlier rosters' token counts at the model's prices (free); a probe of one run per evidence eval | Spend depends mostly on how much a model reasons, which no one knows before it runs. On one three-model roster, earlier rosters' token counts at each model's prices gave ranges as wide as $4–$54 for a model that cost $42, while a two-run probe projected $36, $12, and $28 against actual costs of $42, $11, and $27, for under $1 per model. One run of each of the eight evidence evals would tighten the projection, at about 9% of a roster's cost against about 2%. |
| The `capability` probe | One run of core eval 0 and one of lid-coach eval 15 | One run per batch; the cheapest eval | Core runs (a two-turn workflow change) and coach runs (a review) make up 80 of the roster's 94 runs and differ in shape, so one of each samples both; the cheapest eval would understate both. |
| Cost cap | Per model, checked before each run starts; a run in progress finishes | A cap on the invocation's total; stopping the run in progress | Whether a model is worth its cost is judged per model, and one expensive model should not stop the others' runs. Cost is known only when a turn ends, so the check sits between runs, bounding the overshoot at one run per lane; stopping a run partway would waste what it had already cost and leave nothing to grade. |
| Model check before staging | Stop when OpenRouter lists no such model, or lists it without tool support | Let the first runs fail | A model without tool calling fails every run in the harness. The check names the cause before any container starts, where the batch would otherwise stop after two harness errors that show only the harness's message. |
| Rosters | Named presets in the runner, run in lanes | Per-round shell scripts around single batches; a separate orchestration tool | Hand-written scripts re-derived the same batches and lane split every round. The estimate needs the same batch list to project from, so a preset gives the launch and the estimate one definition. A separate tool would duplicate the runner's preflight, pricing, and output conventions. |
| Concurrency | Lanes of whole batches; runs within a batch stay sequential | Concurrent runs within a batch; strictly sequential runs | Lanes leave each batch's run order, numbering, and two-harness-error rule as they are. Strictly sequential, a roster for a slow model takes most of a day: one model averaged about 6 minutes per run over its 94 runs. |
| Cost probe output | Kept in each suite's workspace as `cost-probe-…` batches, marked `probe`, never graded or recorded | Discarded with the scratch directory; named `alt-model-probe-…` | A probe's transcript shows whether the model works in the harness at all. A name outside `alt-model-*` keeps probe runs out of any grading step that collects a model's batches by name. |
| Interrupt during a follow-up turn | The whole run is `interrupted` | The run keeps its first turn's status, with only the follow-up recorded as interrupted | A first turn that completed would make the run gradable, and its unfinished follow-up would fail every follow-up assertion: the person's stop would be counted against the model. |
| Termination signals | SIGTERM and SIGHUP stop the runner as Ctrl-C does | Ctrl-C only | A roster can run detached for most of a day; stopped by `kill` or a closed terminal without this, it would leave its batches marked `running` and its snapshot on disk. |
| Snapshot contents | Exactly the files the recorded tree ID covers, minus `evals/` and `*-workspace/`, symbolic links kept as links | Every file under `plugins/` minus the excluded directories, gitignored ones included | Gitignored files (editor droppings, caches) are not in the tree ID, so copying them would give the model text its record does not name. |
| Harness-error stop in a roster | Two consecutive harness errors in one batch stop every batch of that model | Each batch keeps its own stop | The stop exists because a bad key, a bad model ID, or an outage would fail every remaining run. Kept per batch, it would spend two runs in each of the model's batches before stopping them all. |
| Runner failure in a roster | Stop every lane; the stopped batches record `runner_error` | Stop only the failing batch | A runner failure (a full disk, a broken runtime) is a fault of the machine, not the model, and usually reaches every lane; carrying on would spend money on runs that fail the same way. |
| Plugins staged per invocation | One snapshot of `plugins/` at the start of the invocation, which every run stages from | A fresh copy for each run; a tree check before each run that aborts on change | A roster can run for most of a day in a checkout someone is working in. Per-run copies would let a mid-roster edit reach later runs under a tree ID recorded before it; a check would abort the roster where the snapshot simply carries on with the text it started with. |
| A model failing the pre-staging check in a roster | Stop the whole invocation before any run | Drop that model and run the rest | A model that fails the check is usually a typo in the model list, which the person running it wants to fix before spending anything. |
| Grading | Out of the runner; done by a frontier-model session with `skill-creator`'s grader | The runner calls a grader model itself | Grading shares one method with Claude runs, and the runner stays a thin wrapper. |
| Node placement | Top-level leaf under the HLD | A leaf under the `linked-intent-dev` sub-HLD; a section of `project-structure` | The runner serves every plugin's suites, so the lowest node that covers all of them is the root. It carries its own design decisions (harness, sandbox, permissions), which would bloat `project-structure`. |

## Open Questions & Future Decisions

### Resolved

1. ✅ Harness: opencode, pinned, in a container.
2. ✅ Runs are local and optional. No CI, no merge gate.
3. ✅ Results are recorded in `tested_with` with a `harness` field.
4. ✅ Parallel runs: a roster's batches run in lanes (`--lanes N`); runs within a batch stay sequential.

### Deferred

1. **Baseline (without-skill) runs.** `skill-creator` pairs each with-skill run with a baseline. Alternate-model baselines would show whether a skill moves a non-Claude model at all, not just whether that model passes.
2. **A second harness.** Running the same model under two harnesses would separate model effects from harness effects. This matters for questions like how LID behaves inside tools that read `AGENTS.md` natively.
3. **A per-batch key.** OpenRouter's key-management API can create a key with a credit limit from a separate provisioning key. The runner could mint one per batch, pass only it into the containers, and delete it when the batch ends, so the contributor's own key never enters a container. This replaces the advice to keep a dedicated low-limit key.
4. **Egress restricted to OpenRouter, or a key-adding proxy.** Either closes the remaining key-exfiltration path outright.
